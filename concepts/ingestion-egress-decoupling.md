# Architectural Decoupling: Ingestion vs. Egress

The **Market Data Gateway (MDG)** enforces a strict architectural decoupling between internal event ingestion (consuming from [[entities/kafka-broker]]) and external client distribution (broadcasting over WebSockets). This architectural separation protects upstream trading infrastructure, isolates consumer poll loops from client-side network jitter, and optimizes message delivery latencies for external market participants.

---

## 1. High-Level Architecture

The MDG acts as an asynchronous boundary between the internal message bus and public-facing distribution channels. Rather than allowing client network I/O to interact directly or synchronously with message broker consumers, the system splits processing into two discrete tiers:

```
           INGESTION TIER                              EGRESS TIER
 
   +----------------------------+
   | `Order Matching Engine`  |
   +----------------------------+
                 |
                 | (Kafka Topics)
                 v
   +----------------------------+
   |   `Kafka Broker Cluster` |
   +----------------------------+
          |              |
          v              v
   +--------------+ +--------------+
   |` | [[Trade-     |
   | Consumer`   | |  Consumer]]  |
   +--------------+ +--------------+
          \              /
           \            /  (In-Memory Method Dispatch)
            v          v
   +-------------------------------+
   |        `ClientManager`      | <=====> `Redis Cache`
   |   (WebSocket Connection Pool) |         (Snapshot State Hydration)
   +-------------------------------+
            |              |
            v              v
   +-------------------------------+
   |   External WebSocket Clients  |
   +-------------------------------+
```

1. **Ingestion Tier**: [[entities/order-book-consumer]] and [[entities/trade-consumer]] subscribe to dedicated Kafka topics (`nte.orderbook.snapshots` and `nte.trades.matched`) across isolated consumer groups (`mdg-orderbook-group` and `mdg-trade-group`).
2. **In-Memory Handover Boundary**: Upon message receipt in Kafka consumer `eachMessage` handlers, payloads are passed directly in-memory to the [[entities/client-manager]].
3. **Egress Tier**: [[entities/client-manager]] maintains the active `Set<WebSocket>` connection pool and executes low-latency non-blocking broadcasts to subscribed clients.

---

## 2. Core Drivers for Decoupling

### 2.1. Mitigating Slow Consumer Backpressure
In a real-time market data feed, external WebSocket clients have diverse network bandwidths, geographic latencies, and TCP buffer capacities. If client socket writes were coupled to Kafka consumer loops:
* A single stalled or slow-reading client could block the `eachMessage` callback.
* Blocked poll loops would delay Kafka heartbeat processing (`max.poll.interval.ms`), causing brokers to consider the consumer dead and trigger cascading partition rebalances.
* By decoupling the two tiers, consumer loops run at full Kafka throughput, handing off messages to [[entities/client-manager]] to iterate over open client sockets independently.

### 2.2. Failure Domain Isolation
* **Client Disconnections**: Sockets disconnecting abruptly or failing mid-transmission are handled within the egress tier (via event listeners and connection state checks in [[concepts/websocket-broadcasting]]). Disconnections never bubble up to abort Kafka transaction offsets or consumer streams.
* **Broker Outages / Rebalances**: If Kafka undergoes partition rebalancing or broker failover, active client WebSocket sessions remain open, and cached order book state can continue to be served via [[entities/redis-cache]] through [[concepts/state-hydration]].

### 2.3. Protocol & Schema Translation
The internal platform architecture relies on compact binary [[entities/protobuf-contracts]] (e.g., `nte.marketdata.OrderBookSnapshot`, `nte.marketdata.TradeTick`) generated by the [[entities/order-matching-engine]]. The external egress tier translates these messages into standardized JSON envelope payloads (`L2_UPDATE`, `TRADE_TICK`) defined in [[entities/runtime-models]] for web and client consuming libraries.

## 3. Ingestion vs. Egress Responsibilities

| Dimension | Ingestion Subsystem (`src/consumers/`) | Egress Subsystem (`src/websockets/`) |
| :--- | :--- | :--- |
| **Primary Components** | [[entities/order-book-consumer]], [[entities/trade-consumer]] | [[entities/client-manager]] |
| **Protocol / Transport** | Apache Kafka TCP binary protocol | WebSocket over TCP (RFC 6455) |
| **Concurrency Model** | Dedicated consumer event loops per topic | Single-threaded Node.js event loop with non-blocking socket dispatch |
| **Scaling Axis** | Topic partitions & [[decisions/independent-consumer-groups]] | Process instances & [[decisions/low-latency-egress-design]] |
| **State Retention** | Offset management in Kafka | Ephemeral connection pool `Set<WebSocket>` & [[decisions/redis-l2-state-caching]] |
| **Wire Contract** | [[entities/protobuf-contracts]] | [[entities/runtime-models]] JSON envelopes |

## 4. Ingestion-to-Egress Handover Flow

The transition of data across this decoupling boundary is illustrated below:

```
Kafka Topic ────────► Consumer.eachMessage() ───► ClientManager.broadcast*() ───► ws.send()
(Broker I/O)          (Worker Thread / Ingestion) (In-Memory Reference Handover)  (Egress Non-Blocking Socket)
```

1. **Ingestion Loop**:
   * [[entities/order-book-consumer]] ingests `nte.orderbook.snapshots`.
   * [[entities/trade-consumer]] ingests `nte.trades.matched`.
2. **Zero-Queue In-Memory Dispatch**:
   Instead of writing to intermediate persistent queues, consumers invoke `this.clientManager.broadcastOrderBook(snapshot)` or `this.clientManager.broadcastTrade(tradeData)`.
3. **Egress Filtering & Dispatch**:
   * [[entities/client-manager]] validates that socket connections are strictly in the `WebSocket.OPEN` ready state.
   * Payloads are serialized into envelope formats and pushed to socket write buffers.
   * Dropped or closed connections are garbage-collected from the active client registry on `'close'` events.

For a comprehensive breakdown of the entire pipeline from matching engine execution to final network delivery, see [[concepts/data-lifecycle]].

## 5. Architectural Considerations & Related Decisions

* **Independent Ingestion Streams**: To prevent high-volume trade bursts from starving order book depth updates, consumer groups are completely separated. See [[decisions/independent-consumer-groups]].
* **Egress Broadcasting Strategy**: Egress avoids heavy serialization inside broadcast loops to maximize fan-out throughput. See [[decisions/low-latency-egress-design]].
* **Snapshot Hydration via Redis**: New clients connecting to the egress tier do not replay Kafka logs; instead, initial state is hydrated directly from [[entities/redis-cache]]. See [[decisions/redis-l2-state-caching]] and [[concepts/state-hydration]].
* **System Overview & Context**: Detailed component interactions are covered in [[summaries/market-data-gateway-overview]] and the root [[index]].
