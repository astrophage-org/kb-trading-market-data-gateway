# WebSocket Broadcasting

The **WebSocket Broadcasting** subsystem in the **Market Data Gateway (MDG)** is responsible for delivering real-time market data ticks and Level 2 (L2) book snapshots to external market participants, algorithmic trading desks, and user interfaces. Operating at the boundary between internal exchange systems and external networks, it manages connection pooling, validates client socket states, and performs low-latency fan-out message dissemination.

---

## 1. Architectural Role in Egress Pipeline

As described in [[concepts/ingestion-egress-decoupling]], the MDG isolates upstream [[entities/kafka-broker]] consumption loops from client-facing distribution networks. The broadcast mechanism transforms high-throughput internal event streams into standardized JSON envelopes and disseminates them concurrently across all active subscribers.

```
+-------------------------------------------------------------------------+
|                       Market Data Gateway (MDG)                         |
|                                                                         |
|  [[entities/order-book-consumer]]            [[entities/trade-consumer]]|
|        (nte.orderbook.snapshots)                    (nte.trades.matched)|
|                    \                                    /               |
|                     \                                  /                |
|                      v                                v                 |
|         +-----------------------------------------------------+         |
|         |              [[entities/client-manager]]            |         |
|         |  Connection Pool: Set<WebSocket> (Port 8080)        |         |
|         +-----------------------------------------------------+         |
+------------------------------------|------------------------------------+
                                     |
           +-------------------------+-------------------------+
           | State Validation (`client.readyState === OPEN`)   |
           | JSON Envelope Serialization                       |
           +-------------------------+-------------------------+
                                     |
             +-----------------------+-----------------------+
             |                       |                       |
             v                       v                       v
      [ WS Client 1 ]         [ WS Client 2 ]         [ WS Client N ]
     (L2_UPDATE/TRADE)       (L2_UPDATE/TRADE)       (L2_UPDATE/TRADE)
```

Broadcasting operates directly downstream of:
- **[[entities/order-book-consumer]]**: Forwards aggregated order book depth snapshots.
- **[[entities/trade-consumer]]**: Forwards confirmed trade match events generated by the [[entities/order-matching-engine]].

## 2. Connection Pooling Lifecycle

The [[entities/client-manager]] maintains an in-memory connection registry using an ES6 `Set<WebSocket>`. This structure provides $O(1)$ addition and deletion of client sockets during lifecycle transitions.

```typescript
// Connection pool initialization in ClientManager
this.wss = new WebSocketServer({ port });
this.wss.on('connection', (ws: WebSocket) => {
    this.clients.add(ws);
    ws.on('close', () => this.clients.delete(ws));
});
```

### Connection Lifecycle Stages:
1. **Handshake & Registration**: When a client completes the HTTP `Upgrade` handshake on port `8080`, the resulting `WebSocket` instance is added to the active `clients` pool.
2. **State Hydration**: Newly connected clients can receive the latest cached market depth via [[concepts/state-hydration]] powered by [[entities/redis-cache]] (see [[decisions/redis-l2-state-caching]]).
3. **Active Broadcasting**: Sockets remain in the pool, receiving periodic depth snapshots and execution ticks.
4. **Deregistration & Eviction**: On receiving a `close` event or detecting a socket termination, the socket reference is immediately pruned from the `Set`, preventing memory leaks and avoiding unnecessary iterations.

## 3. Client State Validation

Before attempting a write operation over the wire, the broadcasting loop evaluates the connection's readiness state. In the `ws` runtime, socket states transition across:
- `WebSocket.CONNECTING` (0)
- `WebSocket.OPEN` (1)
- `WebSocket.CLOSING` (2)
- `WebSocket.CLOSED` (3)

### Validation Implementation:
```typescript
if (client.readyState === WebSocket.OPEN) {
    client.send(payload);
}
```

### Purpose of State Validation:
- **Mitigating Dropped Frame Exceptions**: Writing to sockets in `CLOSING` or `CLOSED` states raises synchronous exceptions in Node.js, risking unhandled errors in the main event loop.
- **Preventing Backpressure Head-of-Line Blocking**: Skipping sockets that are not fully open ensures that connecting or terminating sockets do not impede the distribution loop for healthy subscribers.
- **Fairness & Determinism**: Guarantees that active market participants receive the same market tick in the same event-loop cycle without stalling on dead connections (aligned with [[decisions/low-latency-egress-design]]).

## 4. Fan-Out Dissemination

The fan-out engine exposes two dedicated broadcast methods tailored to specific market event types.

### 4.1. Order Book Snapshot Broadcast (`broadcastOrderBook`)
Distributes aggregated Level 2 book updates parsed from the `nte.orderbook.snapshots` topic (derived from [[entities/protobuf-contracts]] `nte.marketdata.OrderBookSnapshot`).

```typescript
broadcastOrderBook(snapshot: string) {
    for (const client of this.clients) {
        if (client.readyState === WebSocket.OPEN) {
            client.send(JSON.stringify({ type: 'L2_UPDATE', data: snapshot }));
        }
    }
}
```
* **Payload Type**: `L2_UPDATE` (see [[entities/runtime-models]]).
* **Payload Data**: Serialized JSON string containing symbol, bid levels, ask levels, and timestamps.

### 4.2. Trade Tick Broadcast (`broadcastTrade`)
Distributes individual trade execution matches parsed from the `nte.trades.matched` topic (derived from [[entities/protobuf-contracts]] `nte.marketdata.TradeTick`).

```typescript
broadcastTrade(trade: string) {
    for (const client of this.clients) {
        if (client.readyState === WebSocket.OPEN) {
            client.send(JSON.stringify({ type: 'TRADE_TICK', data: trade }));
        }
    }
}
```
* **Payload Type**: `TRADE_TICK` (see [[entities/runtime-models]]).
* **Payload Data**: Serialized JSON string containing trade ID, execution price, quantity, timestamp, and aggressor side.

## 5. End-to-End Data Trajectory

The complete path of a broadcasted market event spans matching, ingestion, and egress:

```
[Matching Core] ──► Kafka Topic ──► MDG Consumer ──► [ClientManager Broadcast] ──► Client Sockets
```

1. **Ingestion**: [[entities/order-book-consumer]] or [[entities/trade-consumer]] receives a Kafka message batch via [[entities/kafka-broker]].
2. **Handoff**: The consumer passes raw stringified or decoded data directly into `ClientManager.broadcastOrderBook()` or `ClientManager.broadcastTrade()`.
3. **Envelope Packaging**: The message is packaged into an event envelope (`{ type, data }`).
4. **Iteration**: The `ClientManager` performs an in-memory loop over `this.clients`, checks `readyState === WebSocket.OPEN`, and invokes `ws.send()`.
5. **Downstream Delivery**: External clients process the event to update order book visualizations or feed algorithmic models. Concurrently, sister services like [[entities/compliance-surveillance-monitor]] and [[entities/trade-settlement-system]] process identical execution streams through internal Kafka topics.

## 6. Performance Characteristics and Design Decisions

* **Independent Ingestion Threads**: Supported by [[decisions/independent-consumer-groups]], preventing trade volume spikes from blocking order book broadcasts.
* **Non-Blocking In-Memory Fan-Out**: Linear $O(N)$ iteration over open sockets with minimal CPU overhead during serialization (see [[decisions/low-latency-egress-design]]).
* **Decoupled Architecture**: Comprehensive breakdown in [[concepts/ingestion-egress-decoupling]] and the broader [[concepts/data-lifecycle]].
