# Redis Cache

The **Redis Cache** is the in-memory key-value storage layer within the **Market Data Gateway (MDG)** architecture. It maintains the most recent Level 2 (L2) order book depth snapshots generated by the [[entities/order-matching-engine]], enabling instantaneous [[concepts/state-hydration]] when external market participants establish new WebSocket connections.

---

## Responsibilities

* **L2 Order Book State Retention**: Persists the latest consolidated market depth snapshot for each active trading instrument symbol.
* **Rapid Client State Hydration**: Serves instantaneous L2 snapshots during client WebSocket connection establishment, ensuring external clients receive full book depth prior to consuming incremental updates (see [[concepts/state-hydration]] and [[decisions/redis-l2-state-caching]]).
* **Decoupling Historical State from Stream Ingestion**: Eliminates the need for new WebSocket connections to query or wait for Kafka topic offsets on [[entities/kafka-broker]], supporting [[concepts/ingestion-egress-decoupling]].
* **Fast State Recovery**: Provides a warm state cache for MDG instance restarts, mitigating initial data starvation during service boot sequences.

---

## Dependencies

* **Upstream Ingestion Tier**: Updated asynchronously by [[entities/order-book-consumer]] as new `nte.orderbook.snapshots` messages arrive from the [[entities/kafka-broker]].
* **Egress & Connection Management**: Read by [[entities/client-manager]] during connection handshakes before enrolling client sockets into the active [[concepts/websocket-broadcasting]] pool.
* **Data Contracts**: Formatted against the [[entities/protobuf-contracts]] schema (`nte.marketdata.OrderBookSnapshot`) and represented by [[entities/runtime-models]] (`OrderBookEvent`).
* **Deployment & Container Orchestration**: Deployed as a dedicated service container (`redis:alpine`) in `docker-compose.yml` alongside the MDG gateway application.

---

## Architectural Role in Data Lifecycle

In the end-to-end [[concepts/data-lifecycle]], the Redis cache acts as a state anchor between continuous streaming events and point-in-time state queries:

```
[order-matching-engine]
          │
          ▼
 Kafka: `nte.orderbook.snapshots`
          │
          ▼
`OrderBookConsumer` ──(Write Snapshot)──► `Redis Cache`
          │                                      ▲
   (Stream Updates)                              │ (Read Initial State)
          │                                      │
          ▼                                      │
  `ClientManager` ─────────────────────────────┘
          │
          ▼
   WebSocket Clients (L2_UPDATE)
```

1. **Write Path**: As the [[entities/order-book-consumer]] processes snapshot messages from Kafka, it updates the corresponding symbol key in Redis.
2. **Read Path**: When a new client connects via WebSocket, [[entities/client-manager]] fetches the latest cached snapshot from Redis to populate the client's local order book state before streaming subsequent live broadcast envelopes.

---

## Key Design Patterns & Decisions

* **Sub-Millisecond Read Latency**: By keeping book snapshots in-memory, the gateway avoids blocking the Node.js event loop during high client connection bursts, adhering to the [[decisions/low-latency-egress-design]].
* **Dedicated State Caching Decision**: Documented in detail in [[decisions/redis-l2-state-caching]], isolating snapshot storage from Kafka topic replays ensures predictable ingress performance and zero consumer group lag on high-volume trading streams.
